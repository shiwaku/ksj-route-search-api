# 負荷試験（2026-11-23・歩行者を入れた本番・1 台と 4 台）

FOSS4G Hokkaido 2026（11/28）のデモで来場者が一斉に触る場面を想定し、歩行者（issue #55）を入れた本番で、同時アクセスの負荷を測った記録。1 台で測ったあと、コンテナを 4 台に増やして同じ条件で測り直した（issue #26）。

- 本番: https://ksj-route-search.shi-works-worker.workers.dev （Cloudflare Containers standard-1 = 0.5 vCPU・4 GiB）
  - 1 台: Version 56d2560c（`CONTAINER_COUNT=1`・`max_instances=1`）
  - 4 台: Version 62545f37（`CONTAINER_COUNT=4`・`max_instances=4`）。Worker がリクエストごとに台をランダムに選ぶ
- 手元: 本番と同じイメージを Docker で `--cpus 0.5 --memory 4g` に絞って直接叩く（Worker・回線を通らない）
- スクリプト: [scripts/load_mix.mjs](scripts/load_mix.mjs)。本番は Cloudflare Access があるので、ログイン済みのブラウザのコンソールで同じ処理を `base='/api'` として流した

## まとめ

1. **4 台にすると、同時 100 人でも最後の人まで 3 秒以内に返る。** 混在 100 人の最遅は 1 台 8.5 秒 → 4 台 2.7 秒、車の到達圏 120 分だけ 100 人は 14.1 秒 → 4.2 秒。エラーは 0 本
2. **1 台でも混在 100 人は目標（10〜15 秒）に入る。** 車だけ 100 人の 14 秒が上の端
3. **1 台では、徒歩が車の後ろで待たされる。** 徒歩 30 分の計算は約 10 ms なのに、混在では中央 5〜6 秒かかった。同時計算の枠（`REACH_CONCURRENCY = 2`）を車と共有しているため。4 台では中央 1.3 秒になり、徒歩専用の枠は作らずに済んだ
4. **コンテナを大きくしても今のままでは速くならない。** SciPy 1.18 の Dijkstra は計算中に GIL を手放さず、4 スレッドで回しても 1 スレッドと同じ時間（1.06 秒 / 1.04 秒、手元で確認）。vCPU を増やすなら uvicorn のプロセスを分ける必要がある。台数を増やすほうが設定だけで済む
5. **起こすのに 1 台あたり約 70 秒。** 4 台を同時に起こしたとき。1 台は起動直後に再起動して `sin19`（シンガポール）に置き直された（ほかの 3 台は `iad23`）。当日は開始前に `/health?instance=0..3` で全台を起こし、`status: ok` と `walk.loaded: true` を確かめる

## 計測の条件

- 同時 N 人が 1 回ずつタップした状況を作る（N 本を一斉に投げ、全部の応答を待つ）。回の間は 15 秒あける
- リクエストごとに別の `X-Client-Id` を付け、端末ごとの回数制限（20 回/10 秒）を人数分に分ける
- シナリオ
  - **混在**（来場者の想定）: 車の到達圏 120 分 40%・徒歩の到達圏 30 分 25%・徒歩 120 分 5%・徒歩の経路 15%・車の経路 15%
  - **車だけ**: 車の到達圏 120 分（`road_class=auto`・高速あり・`format=bin`）
  - **徒歩だけ**: 徒歩の到達圏 30 分（4 km/h）
- 起点: 車は札幌圏・会場（北広島）のまわり、徒歩は札幌・北広島・旭川・函館の市街地。車の経路の終点は千歳付近

## 結果

応答時間（秒）。中央 / 90% / 最遅。

| シナリオ | 手元 1 台 | 本番 1 台 | 本番 4 台 |
|---|---|---|---|
| 混在 30 人 | 1.7 / – / 3.4 | 1.9 / – / 3.3 | 1.0 / 1.6 / 1.7 |
| 混在 60 人 | 3.1 / – / 5.9 | 2.3 / – / 4.5 ※ | 0.8 / 1.5 / 1.6 |
| 混在 100 人 | 3.9 / 7.6 / 8.3 | 3.7 / 7.6 / 8.5 | 1.1 / 2.2 / 2.7 |
| 車だけ 100 人 | 8.2 / – / 15.8 | 7.4 / – / 14.1 | 2.1 / 3.7 / 4.2 |
| 徒歩だけ 100 人 | 1.6 / – / 2.9 | – | 0.4 / 0.6 / 0.8 |

※ 4 回流したうち 1 回だけ 500 が 1 本。再現していない。

### 本番 4 台・混在 100 人の内訳

| 種類 | 本数 | 中央 / 90% / 最遅 |
|---|---|---|
| 車の到達圏 120 分 | 39 | 1.6 / 2.4 / 2.7 |
| 車の経路 | 17 | 0.7 / 0.9 / 1.2 |
| 徒歩の到達圏 30 分 | 24 | 1.3 / 2.2 / 2.3 |
| 徒歩の到達圏 120 分 | 6 | 1.2 / 2.3 / 2.3 |
| 徒歩の経路 | 14 | 0.4 / 0.9 / 1.1 |

台ごとの本数は 35・30・17・18 本（ランダムに選ぶので偏る）。最遅は台 0 の 2.7 秒。

### メモリ（手元）

- 常駐 1.28 GiB（車＋歩行者のグラフ）
- 混在 100 人のピーク 1.81 GiB。4 GiB に十分収まる

## 費用の目安

メモリとディスクは起きている間の確保量、CPU は実際に使った分で課金される（[料金](https://developers.cloudflare.com/containers/platform/pricing/)）。起きている 1 時間あたりのメモリ＋ディスク代は、1 台 約 $0.04・4 台 約 $0.15。10 分アクセスが無ければ眠り、眠っている間は掛からない。
