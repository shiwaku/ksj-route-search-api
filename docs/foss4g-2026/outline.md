### 1. つかみ（2 分）

- 表紙 → すぐ公開版を映す。会場の北広島（トナリエ北広島）をタップ → 120 分 → 480 分で北海道全体が色づく
- 「全国 388 万本の道路から、ここから車で何分かを 1 本ずつ塗っています」
- デモはここで一度だけ。駄目なら予備（`backup-demo.md`）→ 録画の順に切り替える

### 2. 背景（2 分）

- 経路探索・到達圏に使う道路網は、これまで有償（DRM など）が一般的だった
- 2026 年 4 月、国土数値情報 道路データ（全国約 2,400 万本）が CC BY 4.0 で公開
- 発表者のこれまで: ライン → ノード・リンクへの変換、到達圏・公共交通空白地域・津波避難への応用（MIERUNE JCT #03・2026-06）。その時の展望「全国対応 Web API」の続きが今日の話

### 3. 作ったもの（1.5 分）

- 幅員 5.5m 以上の 388 万リンク・371 万ノード・総延長 37.5 万 km（全体の 16%・生成 48 秒）
- 到達圏（道路 1 本ごとに分で色分け・メッシュにしない）と経路探索の Web API ＋ 画面
- 構成図: SvelteKit ＋ MapLibre ／ FastAPI ＋ SciPy ／ PMTiles。公開は Cloudflare Workers ＋ Containers

### 4. 工夫① 探索: グラフをどこに置くか（2.5 分）

- pgRouting と SciPy（メモリ上のグラフ）を同じ道路網で比べた → **結果は完全一致・10〜27 倍速い**（30 分 17 ms vs 315 ms、東京→大阪 267 ms vs 3.3 秒）
- 差はアルゴリズムではなく置き場所: pgRouting は打ち切っても先にテーブルを読むので範囲を変えても時間がほぼ一定
- 経路は直線距離から打ち切りを見積もって倍々に広げる（毎回全国を探さない）。0.5 vCPU で東京→横浜 0.98 → 0.04 秒
- （時間があれば）OSRM・GraphHopper・Valhalla との比較: 経路が一致するのは厳密解の OSRM・GraphHopper。Valhalla は速さのために厳密さを手放している（`docs/routing-engines.md` 8 章・PR #44）

### 5. 工夫② 描画: 何本をいつ塗るか（2.5 分）

- 道路は PMTiles のベクタタイル、色は MapLibre の feature-state で到達時間ごとに付ける
- 詰まった所: 数十万本の feature-state を一度に変えると、タイル枚数 × 本数で重くなる
- 対策: 読み込み済みタイルの道路だけ、太い道から 1 フレーム 4,000 本ずつ塗る → スマホ相当で東京 z11 最初の色 5.8 → 1.0 秒・最長フレーム 4.3 → 0.24 秒
- 広域のズーム（z5〜8）は高速・国道だけ＋簡略化したタイルにして軽くした（#17・z8 120 分の描画 347 ms）
- 図: 塗る前後のフレーム時間のグラフ、到達圏 120 分 / 480 分の画面

### 6. 工夫③ 公開: DB なしで安く載せる（2.5 分）

- DB を持たない構成にして、1 Worker（画面・タイル・API）＋ コンテナ 1 台（0.5 vCPU・4 GiB）
- 起動: 前処理でグラフを読むだけのファイル（.npy）にして 44 → 10 秒、常駐メモリ 2.35 → 1.02 GiB
- 転送: 到達圏の結果を ID 差分＋コストのバイナリにして 120 分で 3.6 → 0.95 MB
- タイル: Worker の Cache API に置いて R2 0.2 秒 → 0.09 秒（無料）
- 費用: 使われていなければ寝る（約 20 秒で起きる）。今日は台数を増やして起こしたまま（#26・#27）
- 図: Cloudflare 構成図

### 7. 割り切りと今後（1.5 分）

- 割り切り: 車のみ・一方通行なし（データに属性がない）・道路分類ごとの固定速度・コンテナの拠点は日本に固定できない（約 200 ms 上乗せ）
- 今後: 経路の階層化（#10）、通行止め・冠水を避ける迂回ルート（#42）、AI チャットからの利用（MCP）
